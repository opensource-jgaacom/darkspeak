# DarkSpeak FileShare Upload Workflow

**Status:** Specification; implementation deferred until interactive read-only FileShare browsing and downloads are verified in the application.

**Dependencies:** `fileshare_authorization.md` (all basic identity/contact/group/path permissions and resource ceilings), `../vfs.md`, `../file_manager.md`, `../protocol.md` (generic checkpoint transfers) and `fileshare_credits.md` **only when exchange is enabled for the receiving identity**. The future upload-specific wire request/response and writable mutation contracts must be finalized before implementation. No standalone upload byte-transfer engine.

## 1. Scope, policy and priority

FileShare uploads are independent of exchange credits. They must work when `credits_enabled=false` (the per-local-identity default). Upload allowance is determined by authenticated contact, currently authorized identity/mount/path, backend writable capability, safe storage limits and explicit file-acceptance policy, **not** by credit balance or whether exchange is configured. The requesting peer cannot enable credits or choose a different local identity.

Upload file acceptance is configurable independently of exchange: automatic or operator/manual. Group policy merges select **Manual over Automatic**; more restrictive duplicate/hash exclusions take precedence and the union of applicable exclusion lists is enforced. The most permissive contact trust upload allowance within fixed hard limits applies where specified. Settings are versioned, persisted and scoped to identity/group/contact following `fileshare_authorization.md`; credit approval and earning ratios are exclusively in `fileshare_credits.md`.

Uploads/mutations must not be implemented before the read-only FTP download milestone is interactively accepted. Subsequent first milestone: a user can upload an ordinary file into an explicitly writable managed VFS mount, review and accept it when required, see it appear as a normal file only after validation/publication, and retrieve the verified bytes. Expanded unusual failures and crash matrices can be automated after the interactive milestone, but access confinement, durable verification and publish isolation are initial mandatory tests.

## 4. Admission, acceptance and integrity

Before accepting a remote upload, check authenticated contact, effective mount/path permissions and RECURSE/path barriers, identity storage assignment, backend `Write` capability, absolute system/backend/identity limits, contact/group quotas, staging reservations, concurrency/rate limits, and object limits. Backend reserves actual capacity before creating or extending content; never rely on a free-space check without reservations. Unknown sizes acquire bounded incremental reservations. Disk-full and quota failures are recoverable, typed outcomes. Remote failures disclose no private paths, disk geometry, excluded hashes or cross-identity presence.

A completed file is **accepted** only after entire expected size and locally calculated SHA-256 match, relevant policy/hash checks pass, and the destination backend commits through its existing durable FileManager lifecycle. Duplicate detection may reject announced hashes early, but never trusts the sender hash as proof. Scope duplicate checks explicitly (target share/identity-visible VFS, or owner-defined list); do not expose the global cross-identity index as an existence oracle. Explicit SHA-256 unwanted/exclusion lists override otherwise permissible uploads. Rejected, incomplete or duplicate uploads earn no credit.

File acceptance and optional credit approval are independent. A policy may permit automatic file acceptance but require operator credit approval, or require operator file acceptance before publication. Manual acceptance uses an isolated, quota-accounted quarantine/pending state inaccessible to normal peers until approved; retain validated hashes and bounded retention. File rejection releases ordinary storage/trust allowances after durable cleanup while retaining minimal anti-duplicate/accounting identifiers. Approval policies must not allow an unreviewed file to become visible where manual file acceptance is required. Approved uploads may remain stored even when their credits are revoked. When identity exchange is enabled, the credits subsystem may create a pending entitlement **only after file acceptance**; when disabled no entitlement or award is created.

## 3. Durable upload coordinator

### 3.1 Durable cross-database upload workflow

Use a coordinator-owned, SQLite-backed **durable intent/step journal** (WAL mode is suitable) for operations crossing the FileManager catalog, FileShare upload registry, duplicate claims and optional credit ledger. FileManager is authoritative for publication/commit outcome; the FileShare coordinator is authoritative for acceptance, duplicate claims and entitlements. No distributed atomic SQL transaction or cross-database atomic visibility is assumed. Each operation has a stable, unguessable `UploadId`/workflow ID, versioned bounded intent and monotonic state: quota/staging reserved → received/verified → duplicate claimed → awaiting acceptance (if required) → committing → file committed → accepted registered → entitlement created (only if exchange enabled) → completed; rollback/abort states are explicit. Persist intent **before** participant action and durable outcome **after**, and make every step idempotently queryable/retryable by stable IDs. Indeterminate commits are reconciled against FileManager's recovered operation result; never blindly repeat publication. Before publication, abort/release; after irreversible publication, prefer forward completion. Hold newly committed content out of ordinary remote VFS visibility until FileShare registration/authorization completes. On startup, reconcile all nonterminal workflows before admitting conflicting work; bounded worker batches must not block the UI.

Duplicate exclusion is enforced with atomic persistent claims keyed by verified SHA-256 plus configured duplicate scope. Acquire all overlapping relevant scope claims in deterministic order; concurrently arriving identical uploads cannot both pass a restrictive policy. A sender-provided hash is only an early rejection hint; locally verified bytes are authoritative. Claims survive crashes until recovery proves completion/abort, never expire solely because a process died mid-commit. Rejected or duplicate uploads earn nothing and cleanup safely. File acceptance and credit approval (when enabled) are separate; pending manually reviewed files stay private and quota-accounted, then, if exchange was enabled for this upload under the settled identity policy, their captured entitlement is created once after acceptance. No accepted upload can earn more than one current credit contribution. Operator approval/revocation and FileManager publication do not assume a shared transaction.



Credit ledger transactions are **optional participants**, never preconditions for uploading when exchange is disabled. Disabling exchange must not leave the upload coordinator waiting for a credit subsystem that is intentionally off. Upload publication and acceptance remain authoritative regardless of any subsequent change to credit settings. Pending uploads must not become visible before operator approval in manual mode.

## 4. Cross-platform logical filenames and storage selection

The remote VFS presents the same UNIX-like names on every host, including case-distinct names and names such as `CON`, `NUL`, `COM1`, and names ending in a dot. Never pass untrusted peer names directly to native Windows filesystem APIs. Preserve exact logical names in the VFS catalog, with opaque backend object IDs as the preferred physical naming mode.

On Windows, **writable FileShare mounts are supported only by a backend that has demonstrated host-independent logical-name semantics and an opaque object-ID physical layer** (or a future explicitly verified equivalent). Externally managed native Windows directories remain **read-only for FileShare**. Do not depend on NTFS case-sensitivity flags, historical POSIX subsystems, WSL presence or the special handling of reserved device names for write safety. An eventual encrypted backend can satisfy the same opaque-object contract but is not required merely to make names portable.

The existing managed-native filename policy v1 is not sufficient for this contract: it rejects some otherwise valid virtual names. The writable feature must not silently rename/reject such names based on server OS. Before enabling uploads, version and migrate/extend the backend's **logical catalog name policy** to support exact portable VFS labels, while keeping physical file names independent of these labels. If the adapter is unavailable or its guarantees cannot be proven, advertise/offer read-only FileShare for that storage; do not pretend writable support. Keep host OS details out of remote error messages.

## 5. Integration, UI and testing

Reuse the application-wide transfer queue and generic `TransferManager`/`TransferSession` for content bytes. Feature-owned upload state controls admission, acceptance, quarantine, configured duplicate/hash policies and final publication. The remote protocol needs stable UploadId, authorized virtual destination, content identity, rejection/cancel and decision correlation, but **must not duplicate generic FileOffer, durable checkpoint negotiation, chunk delivery or hash verification**. Operator review uses the upload section of `fileshare_ui.md`, not a second upload management application.

Focused tests during implementation: accepted regular file, manually approved/rejected file, disabled-credits upload with zero ledger usage, conflicting names on Windows-compatible opaque backend, identity/contact/mount denial, SHA-256 mismatch never published, duplicate hash denial, and restart of a pending verified upload. After interactive acceptance, add full coordinator crash/fault matrix, quota edge cases, races, idempotency, revocation boundaries and diverse backend fixtures.

**No-goals:** credit arithmetic and debit/refund accounting (owned by `fileshare_credits.md`), changes to generic transfer protocol, OS-specific file semantics, specialized device-node transfer, or Windows writable native-path mounting.
